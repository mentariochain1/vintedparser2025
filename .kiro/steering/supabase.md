Single source of truth: Supabase‑hosted PostgreSQL
==================================================

Why we pick it (TLDR)
- PostgreSQL gives relations, JSONB, full‑text search, and GIS for future geo filters.
- Supabase runs PostgreSQL for us and ships Auth, Storage, Realtime, and REST/GraphQL. We can ignore them now and flip them on later.
- Free tier covers 50k MAU and 500 MB. Pro at $25/month gives 8 GB disk, daily backups, and 100k MAU. Our target is 10k MAU and a few million rows, so we fit.
- PITR and daily backups are on. Restore is one click.
- Read replicas are a toggle. Each replica has its own endpoint and balancer.
- The Python client (supabase‑py) is first‑party and async friendly. It plugs into FastAPI cleanly.
- Local dev is simple with the CLI. `supabase start` spins up Postgres, Auth, and Storage. `supabase db push` ships migrations to cloud.
- Starters exist. The fastapi‑supabase template pairs FastAPI, SQLAlchemy, and pytest.

Key architecture decisions
--------------------------

Projects per environment
- supabase‑project‑staging on free
- supabase‑project‑prod on Pro with auto upgrade

Schema layout
- public.items: Vinted listings. Keep a JSONB copy and typed columns you query often.
- public.photos: FK to items. URL and metadata.
- public.users: Telegram users. Link to auth.users.id (UUID).
- public.referrals: inviter and invitee link table.
- public.payments: YooKassa payments with status, amount, and yk_id.

Migrations workflow
```bash
supabase db reset
supabase migration new add_items_table
# edit SQL file …
supabase db push            # deploy to staging
# GitHub Action on merge -> supabase db push --prod
```
All DDL sits in supabase/migrations. You can roll back with the CLI and a PITR timestamp.

Connection strategy in code
```python
from supabase import create_client, Client
import os

SUPA_URL = os.environ["SUPABASE_URL"]
SUPA_KEY = os.environ["SUPABASE_SERVICE_KEY"]  # backend only

supa: Client = create_client(SUPA_URL, SUPA_KEY)  # singleton
```
Service key runs without RLS. Bot‑facing APIs use anon keys and RLS policies.

Scaling knobs
- Read load: add up to two read replicas on Pro. Point the crawler at a replica for heavy SELECTs.
- Write load: bump compute size or add disk as rows grow.
- Connections: Supavisor is on. Add ?connection_limit=100 to the DSN if worker counts rise.

Do we need a read replica on day one? No. One Pro instance handles 10k MAU with room to spare.

- [ ] Add a read replica in a closer region if MAU goes past 100k or latency climbs.

Gotchas and best practices
--------------------------

- Reuse one AsyncClient in the app. Closing and reopening clients wastes sockets and file descriptors.
- Supabase Auth JWT has sub = user UUID. Store it in public.users as the FK.
- Avoid serial. Use bigint generated by default as identity to stay clear of 32‑bit limits.
- Use UPSERT for refreshes:
  ```sql
  insert into items (...) values (...)
  on conflict (id) do update
    set price = excluded.price,
        updated_at = now();
  ```
- Caching photos is optional. Supabase Storage buckets live in the same project and expose S3‑style URLs.

Example: simple reads and writes
--------------------------------
```python
# insert or upsert an item
item = {
    "id": 1234567890,
    "title": "Vintage sneakers",
    "price": 2500,
    "currency": "EUR",
    "raw": {...},  # JSONB
}
supa.table("items").upsert(item, on_conflict="id").execute()

# read latest items for a brand
rows = supa.table("items") \
    .select("*") \
    .eq("brand", "Nike") \
    .order("updated_at", desc=True) \
    .limit(50) \
    .execute()
```

Operations notes
----------------
- Keep the service key only on the backend. Never ship it to the client.
- Set statement timeouts on long tasks in the crawler.
- Track row counts and disk use. Set alerts on 70% disk.
- Back up storage buckets if you cache images.

Supabase‑hosted PostgreSQL gives managed backups, replicas, and clean tooling. We keep one driver and one schema as we grow.
